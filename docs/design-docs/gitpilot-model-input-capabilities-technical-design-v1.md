# GitPilot 平台模型输入能力技术设计 v1

## 1. 背景与目标

平台模型目前由管理员通过模型管理页面配置，桌面端和 GitPilot CLI 再通过平台接口获取模型清单。PI agent 的 `Model.input` 是模型适配层使用的静态能力元数据，不是对供应商接口进行运行时探测的结果。若平台不保存模型能力，适配层只能把所有模型错误地标记为文本模型。

本设计为每个平台模型增加输入模态配置，当前支持：

- `text`：文本输入，所有模型始终包含；
- `image`：图片输入，仅在管理员确认模型和对应平台代理支持图片时开启。

## 2. 数据链路

```text
管理端模型配置
  -> ai_model_config.input_modalities
  -> /api/cli/models.inputModalities
  -> gitpilot-cli 平台模型适配器
  -> PI Model.input
  -> 桌面端/CLI 多模态输入策略
```

平台配置是能力的权威来源。PI 的 `Model.input` 只负责把平台能力转换为 PI 能识别的模型元数据，不承担运行时探测。

## 3. 存储与接口约定

数据库使用逗号分隔字符串保存当前支持的能力：`text` 或 `text,image`。存量模型通过迁移默认获得 `text`。后端请求和摘要使用 JSON 数组 `inputModalities`，服务层负责去重、大小写归一化、合法值校验，并保证始终包含 `text`。

`/api/cli/models` 仅返回安全模型摘要，不返回 API Key 或数据库密文。新增的 `inputModalities` 字段直接透传给 CLI；旧 CLI 或旧平台接口缺少该字段时，CLI 适配器回退为 `["text"]`。

## 4. 管理端交互

CHAT 模型配置显示输入能力复选框：文本固定勾选，图片由管理员选择。EMBEDDING 模型沿用文本默认，不在当前桌面端对话模型能力链路中声明图片输入。保存和编辑均通过同一模型配置接口完成，桌面端与移动端表单保持一致。

## 5. 后续扩展

当前能力只描述模型是否能直接接收图片。图片不支持时，桌面端后续可以根据 `Model.input` 选择 OCR、图片转文本或明确提示用户的 fallback 策略；这些策略不在本次模型管理字段变更中实现。
